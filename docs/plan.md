# PaperPerps — Plan

PaperPerps is a paper-trading clone of the Hyperliquid perpetuals exchange. It uses live
Hyperliquid market data (public, read-only, from **mainnet** by default), but every order is
filled by our own simulation engine. Nothing is placed on-chain.

**Core promises**

- **No login.** Opening the site creates an account.
- **No wallet.** Nothing to connect and nothing to sign.
- **$1,000 mock USD** in every new (or reset) account.
- **Feels like Hyperliquid.** Same markets, leverage limits, order types, fees, funding and
  liquidations, close enough that skills learned here carry over.

**Non-goals (v1)**

- Real or testnet on-chain orders, deposits or withdrawals.
- Spot trading, vaults, staking, sub-accounts, HIP-3 builder markets.
- Mobile-native apps (the web app should still be responsive).
- Using Hyperliquid branding. We copy the mechanics and layout ideas, not the logos, name or
  visual identity. The site states clearly that it is not affiliated with Hyperliquid.

## 1. Decisions so far

| Topic | Decision |
|---|---|
| Execution | **Simulated fills** against the live Hyperliquid order book and trades. No orders are placed on any network. |
| Market data | **Mainnet public data by default** (read-only, nothing signed). Testnet was the original plan, but measurements showed its books are too thin (M1 status, §9). `HL_NETWORK=testnet` still works. |
| Markets | **Top 20 perps** (§4.1). |
| Identity | **Anonymous account + recovery key.** The account is created on first visit, its ID is kept in `localStorage`, and a secret key or link restores it on another device. |
| v1 scope | Trading terminal + **leaderboard**, **account reset**, **liquidations & funding**, **advanced orders** (TP/SL, reduce-only, post-only/IOC, triggers). |
| Reset | **24h cooldown.** Resetting does **not** remove you from the leaderboard (§5.3). |
| Leaderboard | Ranked by **absolute PnL** (§5.4). |
| Liquidations | **Liquidation fee = forfeit the remaining margin**, modeled on HL's backstop liquidation (§4.6). |
| Stack | TypeScript (React) frontend, **Go** backend, Postgres. |
| Hosting | **Railway** (app + Postgres), domain **paperperps.lol** from **Porkbun** (§8.1). |

## 2. User experience

### First visit
1. The frontend finds no account in `localStorage` and calls `POST /accounts`.
2. The backend returns `{ accountId, secret }` and credits $1,000 USDC (mock).
3. A short, dismissable banner says *"Save your recovery key to use this account on another
   device"*, with copy-key and copy-link buttons.
4. The user lands on the default market (BTC-PERP), ready to trade.

### Main trading view (modeled on Hyperliquid's layout)
- **Market selector:** the 20 enabled perps (§4.1), with price, 24h change, volume
  and funding.
- **Chart:** candles from `candleSnapshot` plus a live `candle` subscription, drawn with
  TradingView `lightweight-charts`.
- **Order book and recent trades:** the live Hyperliquid L2 book and trade tape.
- **Order form:** Market / Limit / Stop Market / Stop Limit / TP / SL; leverage slider (capped
  at the asset's `maxLeverage`); cross/isolated toggle; reduce-only, post-only, IOC/GTC; TP/SL
  attached at entry; size in coin or USD; projected liquidation price and fee estimate.
- **Bottom tabs:** Positions, Open Orders, Trade History, Funding History, Order History.
- **Account panel:** equity, available balance, margin used, unrealized PnL, cross margin
  ratio.

### Account management
- **Reset:** puts the account back to $1,000 and clears positions and orders. Limited by a
  24h cooldown. Each reset starts a new **run**, but the leaderboard still counts the PnL you
  made before the reset (see §5.3–5.4).
- **Recovery:** `/restore#<secret>` or pasting the key. The secret is never sent in a query
  string, so it stays out of logs.
- **Handle:** an optional public display name for the leaderboard. Randomly generated by
  default (e.g. `brave-otter-412`).

## 3. Architecture

```
                 ┌────────────────────────── Hyperliquid TESTNET ─────────────────────────┐
                 │  wss://api.hyperliquid.xyz/ws           https://.../info (REST)         │
                 └───────────────┬────────────────────────────────────┬───────────────────┘
                                 │ l2Book, trades, allMids,            │ meta, metaAndAssetCtxs,
                                 │ activeAssetCtx, candle              │ candleSnapshot, fundingHistory
                                 ▼                                     ▼
┌──────────────────────────────────────── Go backend (single process, v1) ───────────────────────┐
│                                                                                                 │
│  Market Data Service ──► in-memory MarketState (book, mark, oracle, mid, funding, trades)      │
│          │                         │                                                            │
│          │ fan-out                 │ events (book update / trade / mark update)                 │
│          ▼                         ▼                                                            │
│  Client WS Gateway ◄──────  Matching & Risk Engine  ──► Ledger (fills, fees, funding, PnL)     │
│          ▲                   (one goroutine per market;   │                                     │
│          │                    account risk loop)          ▼                                     │
│  REST API (accounts, orders, history, leaderboard) ──► Postgres                                 │
└─────────────────────────────────────────────────────────────────────────────────────────────────┘
                                 ▲
                                 │ REST + WS
                     ┌───────────┴───────────┐
                     │  React + TS frontend  │
                     └───────────────────────┘
```

### 3.1 Market Data Service
- Opens **one** upstream websocket to Hyperliquid and subscribes to `l2Book`, `trades` and
  `activeAssetCtx` for each of the 20 enabled perps, plus `allMids`.
- **Data source is config:** `HL_NETWORK=mainnet` (default) or `HL_NETWORK=testnet`. Both
  use only the public, unauthenticated info/ws API, with no keys and no signing. Switching
  needs a restart only; orders, positions and ledger are unaffected. Prices can jump when
  switching, so restart while the market is halted: block new orders, recompute margin on
  the new mark price, then resume.
- Keeps an authoritative in-memory `MarketState` per asset: top-N book levels, mark price,
  oracle price, mid, current funding rate, open interest and the last trades.
- Refreshes `meta` periodically to pick up listings and delistings, `szDecimals` and
  `maxLeverage`. Testnet listings change more often than mainnet.
- Reconnects with backoff. If upstream goes stale (no updates for X seconds), the market is
  marked **halted**: new orders are rejected and liquidations pause, so stale data never
  causes a liquidation.
- **Runs on every instance, not just the engine leader.** The feed is read-only, so the
  standby instance also gets live data during a deploy, and clients connected to it see
  live prices.
- **Market data is proxied to clients** instead of each browser connecting to HL directly.
  Users then see exactly the book we fill against, and we stay within HL's per-IP
  connection and subscription limits.

### 3.2 Matching & Risk Engine
**As built (M2):** one engine goroutine owns all trading state (accounts in use, resting
orders by coin). It processes API commands and market events (book changes, new trades)
in sequence, so cross-margin math never races and needs no locks.
- Each change is committed to Postgres in a single transaction before memory is updated.
- Market events reach the engine through a buffered queue that never blocks the feed. If
  the queue is full, the event is dropped, which only delays a fill until the next event.
- At about 100 market events/second across 20 coins this is plenty. Splitting into
  per-market goroutines (the original idea) only becomes worth it if profiling says so.
- The risk loop (liquidations, funding) runs on the same goroutine, once a second.

### 3.3 Ledger & persistence
- Postgres is the source of truth for accounts, orders, fills, positions and ledger entries.
- Engine state (open orders, positions) is rebuilt from Postgres at startup.
- Every balance change is an append-only `ledger_entries` row (fill PnL, fee, funding,
  liquidation, reset). The account balance always equals the sum of its entries.
- Redis is not needed for v1 because a single process holds the hot state. Add it only when
  we scale horizontally.

### 3.4 API surface

Built (M1–M2):

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/accounts` | Create an anonymous account → `{accountId, secret, handle}` |
| GET | `/api/me` | Balance, positions (incl. leverage settings), open orders, margin summary at live marks |
| GET | `/api/me/orders`, `/api/me/fills`, `/api/me/funding` | History (latest 200) |
| PUT | `/api/me/leverage/{coin}` | Set leverage `{leverage}` |
| PUT | `/api/me/margin-mode/{coin}` | `{mode: cross\|isolated}`; only with no position or orders on the coin |
| POST | `/api/me/isolated-margin/{coin}` | `{amount}`: positive adds, negative removes |
| POST | `/api/orders` | Place a market or limit (GTC) order: `{coin, side, type, sz, px?}` |
| DELETE | `/api/orders/{id}` | Cancel an open order |
| GET | `/api/markets` | Tickers for the enabled markets |
| GET | `/api/markets/{coin}/candles?interval=` | Last 500 bars, cached 10s |
| GET | `/api/status` | Version, engine leader/standby, network, markets |
| WS | `/ws` | Topics: `markets`, `book:<coin>`, `trades:<coin>`, and private `account:<id>` (needs `token`) |

There is no separate restore endpoint. A recovery link (`/restore#<secret>`) just makes the
browser use that secret.

Planned:

| Method | Path | Purpose | Milestone |
|---|---|---|---|
| PATCH | `/api/me` | Set handle, leaderboard opt-in | M5 |
| POST | `/api/me/reset` | Reset to $1,000 (cooldown enforced) | M5 |

Auth: `Authorization: Bearer <secret>`. Only `sha256(secret)` is stored. Errors are

`min_notional`, `invalid_price`, `invalid_size`, `market_stale` and `no_liquidity`, and
return `503 engine_unavailable` while a deploy hands over the engine.

## 4. Trading simulation rules

The engine aims to match Hyperliquid's documented behavior. Every numeric parameter (fees,
cooldowns, thresholds) lives in config so it can be tuned to match HL.

### 4.1 Instruments
- **Top 20 perps**, held as a config list (`MARKETS=BTC,ETH,SOL,...`), not computed live.
  - Seed it from **mainnet** 24h notional volume (`metaAndAssetCtxs`), since testnet
    volume says little about what people actually trade.
  - Each coin must also be listed on testnet. Anything missing there is skipped and the
    next coin by volume takes its place.
  - Review it manually (e.g. monthly). A coin removed from the list becomes **close-only**:
    no new positions, reduce-only orders allowed. It is hidden once nobody holds it.
  - **Initial list (from mainnet 24h volume on 2026-10-09):** `BTC, ETH, HYPE, NEAR, SOL,
    PUMP, VVV, WLD, LIT, SUI, ZRO, DOGE, MET, PONS, ONDO, ADA, TAO, FARTCOIN, XPL, XMR`.
    ZEC, XRP, ENA, STRK and UNI ranked in the top 20 on mainnet but aren't listed on
    testnet, so they were skipped. Since the default is now mainnet, they could be added.
    Keeping every coin valid on both networks means switching networks never strands an
    open position.
- Each market uses its `szDecimals`, tick/price rules and `maxLeverage` from the **data
  network's** `meta`. The two networks don't always agree: on 2026-10-09 SOL was 20× on
  mainnet but 10× on testnet, and NEAR was 10× on mainnet but 20× on testnet. Leverage
  limits therefore change when `HL_NETWORK` changes. Existing positions above a new cap stay
  open, but can't be increased.
- Orders are validated the way HL validates them: price significant figures and decimals,
  size decimals, and minimum order value (about $10 notional).

### 4.2 Market orders
- Walk the **current L2 snapshot** level by level, filling at each level's price until the
  size is filled. The result is a VWAP fill with realistic slippage.
- Slippage protection: reject or cap the fill if the VWAP moves more than X% from mid, like
  HL's market-order slippage limit.
- **Known simplification:** our users don't consume real liquidity, so two users can both
  "take" the same level. Option: deplete a level within a single snapshot for that account,
  so one large order can't fill the same level twice.
- Taker fee.

### 4.3 Limit orders
- If the order would cross the book on arrival, it executes like a taker up to its limit
  price, and any remainder rests (GTC), is cancelled (IOC), or the order is rejected
  (post-only / ALO).
- **Resting fills:** a resting order fills when the live **trade tape trades through**
  its price (strictly better than the limit), or when the best opposite quote crosses it.
  A trade that only *touches* the price doesn't fill it, because we can't know our place in
  the queue. This rule is conservative on purpose.
- Partial fills: fill at most the traded size seen at or through our price (optional; v1 can
  fill completely on the first cross).
- Maker fee.

### 4.4 Trigger orders (Stop / TP / SL)
- Trigger on **mark price**, as HL does.
- When triggered, a Stop/TP/SL Market order runs as a market order. A Stop/TP/SL Limit order
  becomes a limit order.
- TP/SL attached to an entry order is a **position-linked** pair: when one fills or the
  position closes, the other is cancelled. Sizes shrink with the position.
- Reduce-only is enforced when the order is placed and again when it fills. A reduce-only
  order can never flip or grow a position.

### 4.5 Margin
- Each account picks **cross or isolated** per asset, and leverage from 1× to `maxLeverage`.
- Initial margin = `notional / leverage`.
- Maintenance margin follows HL's rule: half the initial margin at max leverage, so
  `MMR = 1 / (2 × maxLeverage)`.
- **Margin tiers are not modeled.** On mainnet (checked 2026-10-09) the second tier starts
  at $3M of notional for ONDO and XPL, and at $20M–$150M for the rest. A $1,000 account
  would need hundreds of times its money in profit to reach that. Revisit if the leaderboard
  ever shows accounts that large.
- **Isolated margin is a slice of the cash balance** set aside for one position:
  - Opening or adding allocates initial margin for the added size.
  - Reducing releases it in proportion; closing releases all of it.
  - Funding on an isolated position is paid from its margin.
  - Cross value = balance − isolated margin + cross uPnL. Available =
    cross value − cross initial margin − order margin.
  - You can add margin, or remove it down to the position's initial margin.
  - Margin mode can only change with no position or orders on the coin, and leverage
    can't change while an isolated position is open.
- Unrealized PnL uses the **mark price**.
- Opening an order needs enough available margin, counting resting orders that would
  increase the position.

### 4.6 Liquidations
- The risk loop re-checks every account with open positions once a second. Isolated
  positions are checked first. A market with stale data is never liquidated, and if any
  of an account's cross positions is stale, the whole cross check waits.
- **Cross:** liquidate when account value < total cross maintenance margin.
  **Isolated:** liquidate per position when its isolated margin + uPnL < its maintenance
  margin.
- Execution: close the position by walking the book like a market order. If the book is too
  thin, close at mark price.
- **Liquidation fee: forfeit the remaining margin.** HL itself charges no explicit
  liquidation fee. In its *backstop* liquidation, though, the liquidated positions and
  their margin pass to the liquidator vault, and "the maintenance margin is not returned to
  the user". We use that backstop outcome as our fee. After the close, the user loses:
  - **Isolated:** the margin left in that position. Cross margin and other positions are
    untouched.
  - **Cross:** the remaining cross equity. Isolated positions are untouched.

  Liquidation only happens once equity is already below maintenance margin, so the fee is
  bounded by MM (1.25%–16.7% of notional depending on the asset). It can never push equity
  below $0, and it needs no arbitrary rate to tune.
  - Lesson for users: on PaperPerps, getting liquidated wipes out that margin, like the
    worst case on HL.
  - The fee is charged on top of the normal taker fee, appears as its own `liquidation_fee`
    ledger entry, and is shown in the liquidation notification.
  - `LIQUIDATION_MODE=forfeit` is the default. `LIQUIDATION_MODE=market` keeps the
    remainder like HL's normal market liquidation, in case forfeiting feels too harsh in
    practice.
- If the close realizes more loss than the margin at stake (prices gapped through the
  liquidation price), the excess is credited back as a `bad_debt` ledger entry. The
  backstop absorbs it, so isolated losses stop at the isolated margin and cross equity stops
  at $0. Users can never owe money.
- If the book is too thin, whatever it can't absorb closes at the mark price.
- **Open orders are cancelled:** all of them on a cross liquidation, and the coin's orders
  on an isolated one.
- The user gets a toast with the liquidation fee. The fills are marked `is_liquidation` in
  trade history.

### 4.7 Funding
- Hourly, on the HL schedule. Payments are idempotent, keyed by
  `(account, coin, funding_hour)`, so a restart or redeploy near the hour can't charge twice.
  Each position is charged or credited
  `size × oraclePrice × fundingRate`, using the live funding rate from
  `activeAssetCtx` / `metaAndAssetCtxs`.
- Longs pay shorts when the rate is positive.
- Every payment is recorded in the ledger and shown in Funding History.
- **As built:** settled at the first risk tick after each hour boundary, using the live
  hourly rate and oracle price. The last settled hour is stored in `engine_state`.
  - Hours missed while the engine was down are not back-filled.
  - Stale markets skip that hour.
  - The first hour after a fresh start is skipped, so a new database never charges
    immediately.

### 4.8 Fees
- Mirror HL's base-tier perp fees (taker ≈ 0.045%, maker ≈ 0.015%; confirm against current
  docs). No volume tiers in v1.

## 5. Accounts, identity and anti-abuse

### 5.1 Identity
- `accountId` (UUIDv7, public) + `secret` (32 random bytes, base64url, private).
- The frontend stores both in `localStorage`. The secret also works as a portable recovery
  key or link.
- No email, no password, no PII.

### 5.2 Abuse controls
- Rate-limit account creation per IP. Without this, people farm throwaway accounts to game
  the leaderboard.
- Rate-limit order placement per account.
- Leaderboard eligibility thresholds (see §5.4).

### 5.3 Reset
- **24h cooldown** between resets (`RESET_COOLDOWN=24h`).
- Cancels all orders, closes all positions with no PnL impact (a hard wipe), sets the
  balance back to $1,000 and starts a new run.
- **Resetting does not remove you from the leaderboard or erase your history.** The new
  $1,000 is a fresh *bankroll*, not a fresh *score*: realized and unrealized PnL from earlier
  runs still counts (see §5.4). This blocks "blow up, reset, repeat" gaming.
- Open positions at reset time are wiped at no PnL impact. Their **unrealized PnL at the
  moment of reset is locked into the leaderboard score** as if they had been closed at mark.
  Otherwise a reset would be a free escape from a losing position.

### 5.4 Leaderboard
- Ranks by **absolute PnL in USD**, summed **across all runs** of the account.
  - Score = Σ(realized PnL − fees ± funding − liquidation fees) + current unrealized PnL
    (at mark).
  - Equivalently: total current equity − $1,000 × number of runs, adjusted for the
    unrealized PnL locked in at each reset.
- Windows: 24h, 7d, 30d, all-time. A window score is the change in that cumulative PnL over
  the window, so it also spans resets.
- Eligibility: at least **5 trades** and an account at least **24 hours** old, to filter out
  lottery tickets (`LEADERBOARD_MIN_TRADES=5`, `LEADERBOARD_MIN_AGE=24h`).
- Shows handle, PnL, volume, number of trades and number of resets. Opt-out is possible.
- Computed from periodic equity snapshots (e.g. every 5 min) stored in `equity_snapshots`.
  The same snapshots drive the account's PnL chart.

## 6. Data model (initial)

```
accounts          id, secret_hash, handle, leaderboard_opt_in, created_at, last_reset_at, current_run_id
runs              id, account_id, started_at, ended_at, starting_balance
ledger_entries    id, account_id, run_id, kind(fill_pnl|fee|funding|liquidation|reset|deposit), amount, ref_id, created_at
positions         account_id, coin, size(signed), entry_px, margin_mode, leverage, isolated_margin, updated_at
orders            id, account_id, coin, side, type, px, trigger_px, sz, filled_sz, tif, reduce_only, post_only,
                  parent_id/oco_group, status, created_at, updated_at
fills             id, order_id, account_id, coin, side, px, sz, fee, liquidity(maker|taker), closed_pnl, is_liquidation, created_at
funding_payments  id, account_id, coin, size, rate, oracle_px, amount, ts
equity_snapshots  account_id, run_id, ts, equity, cumulative_pnl
```

`cumulative_pnl` is the leaderboard score at snapshot time (§5.4). Storing it per snapshot
makes window queries a simple difference between two rows.

All money values are **fixed-point decimals** (`shopspring/decimal` in Go, `numeric` in
Postgres). Never floats.

### 8.1 Deployment (Railway + Porkbun)

**Railway project layout**

| Railway service | What it is |
|---|---|
| `app` | One Go service built from the root multi-stage `Dockerfile` (Railway auto-detects it): build the Vite frontend, build the Go binary, copy both into a small runtime image. The Go server serves the static SPA, the REST API (`/api/*`) and the websocket (`/ws`) **from one origin**, so there is no CORS and only one domain to wire up. |
| `postgres` | Railway's managed Postgres. `DATABASE_URL` is injected into `app` with a variable reference. |

**Config (Railway variables):** `DATABASE_URL`, `HL_NETWORK`, `MARKETS`, `RESET_COOLDOWN`,
`LIQUIDATION_MODE`, `TAKER_FEE_RATE`, `MAKER_FEE_RATE`, `LEADERBOARD_MIN_TRADES`,
`LEADERBOARD_MIN_AGE`, `PORT` (set by Railway). The full list with defaults is in
`.env.example`.

**Service settings live in the Railway dashboard, not in a repo config file.** Railway's
`railway.toml` (Config as Code) is deprecated and stops working for legacy services on
2026-12-01. Its replacement, Infrastructure as Code (`.railway/railway.ts`), doesn't yet
document Dockerfile builds. Revisit IaC once it does. Step-by-step setup is in
`docs/deploy.md`.

**Single engine instance**
- The engine is stateful, so `app` runs with **1 replica**.
- Railway deploys can briefly run the old and new containers side by side. To stop both
  from matching orders, charging funding or liquidating at once, the engine takes a
  **Postgres advisory lock** on a dedicated connection. Only the lock holder runs the engine
  and the upstream feed. A new container waits for the lock. The old one releases it on
  `SIGTERM`, and if it is killed outright, Postgres releases the lock when its connection
  drops.
- **Health check (`/healthz`) passes as soon as HTTP is up and the DB is reachable, not
  when the engine holds the lock.** Railway only stops the old container once the new one
  is healthy. Gating health on the lock would deadlock: the new container waits for the
  lock, and the old one never stops. `/api/status` reports `engine: leader|standby`, and
  trading endpoints return `503 engine_starting` until the lock is held.
- Expect a few seconds of order-entry downtime per deploy. The UI shows "reconnecting…" and
  the client websocket resubscribes on its own.
- If the leader loses its lock connection, the process exits and Railway restarts it.
  Running the engine without the lock is never allowed.

**Domain (Porkbun → Railway)**
1. Buy `paperperps.lol` on Porkbun.
2. In Railway, open `app` → Settings → Networking → *Custom Domain*, add the domain, and
   note the target Railway gives you.
3. In Porkbun DNS:
   - **Apex** (`paperperps.lol`): add an **ALIAS** record to the Railway target, since apex
     domains can't use CNAME.
   - **`www`**: add a **CNAME** to the same target, and redirect `www` → apex in the app.
4. Railway issues the TLS certificate automatically once DNS resolves.

**Cost note:** with one always-on service plus Postgres this should stay small, but the
upstream websocket keeps the service busy around the clock, so serverless/sleep modes can't
be used. Watch Railway usage in the first weeks.

## 10. Risks

| Risk | Mitigation |
|---|---|
| **Upstream data outages** (HL API downtime or disconnects) | Automatic reconnect with backoff; markets flagged stale after 30s; stale-data halts for fills and liquidations (M3). Testnet's data quality risk is avoided by defaulting to mainnet. |
| Fill realism (no queue position, no market impact) | Conservative trade-through rule for limit orders; per-snapshot level depletion; document the simplifications in a "How fills work" page. |
| HL API rate/subscription limits | One upstream connection shared by all users; cache candles server-side. |
| Leaderboard gaming via throwaway accounts (absolute PnL rewards max-leverage lottery bets across many accounts) | Per-IP creation limits; eligibility thresholds; resets don't erase losses (§5.3). |
| Redeploys on Railway overlapping two engine instances | Postgres advisory lock + graceful shutdown; health check independent of lock; idempotent funding (§8.1). |
| Lost secret = lost account | Prompt users clearly to save the recovery key; accepted trade-off of no-login. |
| Stateful single process limits scale | Fine for v1. Later, shard markets across engine instances behind a message bus. |
